# synk ai — Database Schema Design

## Goals

- Fully satisfy issue **1.4** in `ROADMAP.md`.
- Support future roadmap requirements (deduplication, retries, dashboard history, manual runs, config evolution).
- Support multiple Git providers (`github`, `gitlab`, `bitbucket`) without schema rewrites.
- Keep core read/write paths efficient at high run volumes.

## ORM Decision

**ORM: Prisma 7** (`@prisma/client` + `@prisma/adapter-pg`).

Rationale: Better Auth's first-class adapter is `prismaAdapter`, which requires Prisma. The auth schema (`packages/db/src/schemas/auth.prisma`) is generated by Better Auth's organization plugin and is Prisma-native. Using Drizzle alongside would introduce dual-ORM complexity with no benefit; Prisma is the sole ORM for this project.

The schema lives in `packages/db/src/schemas/` as multiple `.prisma` files (Prisma's multi-file schema feature). Prisma merges them at generation/migration time.

> **Drizzle references in earlier docs/roadmap items are superseded by this decision.**

## Design Principles

- Use UUID primary keys internally.
- Model external identities as `(provider, provider_*_id)` instead of provider-specific columns.
- Keep query-critical fields relational; use JSONB for evolving payloads/config.
- Enforce idempotency with unique constraints.
- Track retries and webhook receipts in append-only tables for observability.

## Auth Integration

The auth layer (`auth.prisma`) defines `User`, `Organization`, and membership/invitation models managed by Better Auth's organization plugin. The app domain connects to auth through `Organization` as the **mandatory tenancy boundary**.

```
User <──[Member]──> Organization ──[owns]──> ProviderInstallation
                                                   └──> ProviderRepository
                                                              └──> AnalysisRun
                                                                       └──> AnalysisRunAttempt
WebhookDelivery (no FK; linked by provider + external string IDs)
```

**Personal org convention:** Users who install the app without an organizational context automatically get a personal `Organization` created at the application layer on first login. This is enforced at the application layer, not the schema layer.

**Access-control query pattern** (dashboard: "what can this user see?"):

```sql
SELECT pi.* FROM provider_installation pi
JOIN member m ON m.organization_id = pi.organization_id
WHERE m.user_id = $userId;
```

**Composite FK limitation:** Prisma does not support composite foreign keys. The DATABASE.md constraints `FOREIGN KEY (installation_id, provider) -> provider_installations(id, provider)` and `FOREIGN KEY (repository_id, provider) -> provider_repositories(id, provider)` cannot be expressed in Prisma. Integrity of the `provider` denormalization on child tables is enforced at the application layer. This is an accepted trade-off given Prisma's ergonomic benefits.

## Canonical Provider-Agnostic Schema (v2)

### Enums

- `vcs_provider`: `github | gitlab | bitbucket`
- `installation_status`: `active | suspended | deleted`
- `repository_status`: `active | archived | removed`
- `run_status`: `queued | running | completed | skipped | failed | canceled`
- `run_trigger_type`: `push | merge | manual`
- `attempt_status`: `running | failed | completed`
- `webhook_status`: `received | processed | ignored | failed`

### 1) `provider_installations`

Tenant/app installation boundary for any VCS provider.

- `id UUID PK`
- `organization_id TEXT NOT NULL FK -> organization(id)`
- `provider vcs_provider NOT NULL`
- `provider_installation_id TEXT NOT NULL`
- `provider_account_id TEXT NOT NULL`
- `account_login TEXT NOT NULL`
- `account_type TEXT NOT NULL` (`User` | `Organization` | provider-equivalent)
- `status installation_status NOT NULL DEFAULT 'active'`
- `installed_at TIMESTAMPTZ NOT NULL DEFAULT now()`
- `deleted_at TIMESTAMPTZ NULL`
- `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`
- `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()`

Constraints:

- `UNIQUE (provider, provider_installation_id)`
- `UNIQUE (provider, provider_account_id, provider_installation_id)`
- `UNIQUE (id, provider)` (needed if child tables use composite FK `(id, provider)`)

Indexes:

- `INDEX (provider, status)`
- `INDEX (account_login)`

### 2) `provider_repositories`

Repositories connected to an installation.

- `id UUID PK`
- `installation_id UUID NOT NULL FK -> provider_installations(id)`
- `provider vcs_provider NOT NULL`
- `provider_repository_id TEXT NOT NULL`
- `owner_login TEXT NOT NULL`
- `name TEXT NOT NULL`
- `full_name TEXT NOT NULL`
- `default_branch TEXT NOT NULL`
- `status repository_status NOT NULL DEFAULT 'active'`
- `is_active BOOLEAN NOT NULL DEFAULT true`
- `docs_config JSONB NOT NULL DEFAULT '{}'::jsonb`
- `last_synced_at TIMESTAMPTZ NULL`
- `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`
- `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()`

Constraints:

- `UNIQUE (provider, provider_repository_id)`
- `UNIQUE (installation_id, full_name)`
- `UNIQUE (id, provider)` (needed if child tables use composite FK `(id, provider)`)
- `FOREIGN KEY (installation_id, provider) -> provider_installations(id, provider)` (enforced at app layer in Prisma)

Indexes:

- `INDEX (installation_id)`
- `INDEX (provider, is_active)`
- `INDEX (provider, full_name)`
- `GIN (docs_config)`

### 3) `analysis_runs`

One row per run for push/merge/manual triggers.

- `id UUID PK`
- `repository_id UUID NOT NULL FK -> provider_repositories(id)`
- `provider vcs_provider NOT NULL`
- `trigger_type run_trigger_type NOT NULL`
- `trigger_ref TEXT NOT NULL`
- `trigger_commit_sha TEXT NOT NULL`
- `trigger_merge_request_number INTEGER NULL`
- `trigger_meta JSONB NOT NULL DEFAULT '{}'::jsonb`
- `status run_status NOT NULL`
- `result JSONB NOT NULL DEFAULT '{}'::jsonb`
- `docs_affected BOOLEAN NULL`
- `doc_pr_number INTEGER NULL`
- `doc_pr_url TEXT NULL`
- `token_usage JSONB NOT NULL DEFAULT '{}'::jsonb`
- `error TEXT NULL`
- `attempt_count INTEGER NOT NULL DEFAULT 0`
- `queued_at TIMESTAMPTZ NOT NULL DEFAULT now()`
- `started_at TIMESTAMPTZ NULL`
- `completed_at TIMESTAMPTZ NULL`
- `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`
- `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()`

Constraints:

- `UNIQUE (repository_id, trigger_commit_sha, trigger_type)`
- `FOREIGN KEY (repository_id, provider) -> provider_repositories(id, provider)` (enforced at app layer in Prisma)

Indexes:

- `INDEX (repository_id)`
- `INDEX (status)`
- `INDEX (repository_id, created_at DESC)`
- `INDEX (repository_id, status, created_at DESC)`
- `INDEX (provider, trigger_commit_sha)`

### 4) `analysis_run_attempts`

Per-attempt retry/diagnostic history.

- `id UUID PK`
- `run_id UUID NOT NULL FK -> analysis_runs(id) ON DELETE CASCADE`
- `attempt_number INTEGER NOT NULL`
- `status attempt_status NOT NULL` (`running` | `failed` | `completed`)
- `error TEXT NULL`
- `started_at TIMESTAMPTZ NOT NULL DEFAULT now()`
- `finished_at TIMESTAMPTZ NULL`
- `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`

Constraints:

- `UNIQUE (run_id, attempt_number)`

Indexes:

- `INDEX (run_id)`
- `INDEX (status)`

### 5) `webhook_deliveries`

Cross-provider webhook idempotency and diagnostics.

- `id UUID PK`
- `provider vcs_provider NOT NULL`
- `delivery_id TEXT NOT NULL`
- `event_type TEXT NOT NULL`
- `provider_installation_id TEXT NULL` (raw string — no FK; survives installation deletion)
- `provider_repository_id TEXT NULL` (raw string — no FK)
- `signature_valid BOOLEAN NOT NULL`
- `payload_hash TEXT NOT NULL`
- `received_at TIMESTAMPTZ NOT NULL DEFAULT now()`
- `processed_at TIMESTAMPTZ NULL`
- `status webhook_status NOT NULL DEFAULT 'received'`
- `error TEXT NULL`

Constraints:

- `UNIQUE (provider, delivery_id)`

Indexes:

- `INDEX (provider, event_type, received_at DESC)`
- `INDEX (provider, provider_installation_id, received_at DESC)`
- `INDEX (provider, provider_repository_id, received_at DESC)`

## Prisma Schema (`packages/db/src/schemas/app.prisma`)

The Prisma implementation of the v2 schema above. The `Organization` model is defined in `auth.prisma` (managed by Better Auth); `app.prisma` holds the forward FK and `auth.prisma` holds the back-relation.

```prisma
enum VcsProvider {
  github
  gitlab
  bitbucket
  @@map("vcs_provider")
}

enum InstallationStatus {
  active
  suspended
  deleted
  @@map("installation_status")
}

enum RepositoryStatus {
  active
  archived
  removed
  @@map("repository_status")
}

enum RunStatus {
  queued
  running
  completed
  skipped
  failed
  canceled
  @@map("run_status")
}

enum RunTriggerType {
  push
  merge
  manual
  @@map("run_trigger_type")
}

enum AttemptStatus {
  running
  failed
  completed
  @@map("attempt_status")
}

enum WebhookStatus {
  received
  processed
  ignored
  failed
  @@map("webhook_status")
}

model ProviderInstallation {
  id                     String               @id @default(uuid())
  organizationId         String
  organization           Organization         @relation(fields: [organizationId], references: [id])
  provider               VcsProvider
  providerInstallationId String
  providerAccountId      String
  accountLogin           String
  accountType            String
  status                 InstallationStatus   @default(active)
  installedAt            DateTime             @default(now())
  deletedAt              DateTime?
  createdAt              DateTime             @default(now())
  updatedAt              DateTime             @updatedAt
  repositories           ProviderRepository[]

  @@unique([provider, providerInstallationId])
  @@unique([provider, providerAccountId, providerInstallationId])
  @@unique([id, provider])
  @@index([provider, status])
  @@index([accountLogin])
  @@map("provider_installations")
}

model ProviderRepository {
  id                   String               @id @default(uuid())
  installationId       String
  installation         ProviderInstallation @relation(fields: [installationId], references: [id])
  provider             VcsProvider
  providerRepositoryId String
  ownerLogin           String
  name                 String
  fullName             String
  defaultBranch        String
  status               RepositoryStatus     @default(active)
  isActive             Boolean              @default(true)
  docsConfig           Json                 @default("{}")
  lastSyncedAt         DateTime?
  createdAt            DateTime             @default(now())
  updatedAt            DateTime             @updatedAt
  analysisRuns         AnalysisRun[]

  @@unique([provider, providerRepositoryId])
  @@unique([installationId, fullName])
  @@unique([id, provider])
  @@index([installationId])
  @@index([provider, isActive])
  @@index([provider, fullName])
  @@map("provider_repositories")
}

model AnalysisRun {
  id                        String               @id @default(uuid())
  repositoryId              String
  repository                ProviderRepository   @relation(fields: [repositoryId], references: [id])
  provider                  VcsProvider
  triggerType               RunTriggerType
  triggerRef                String
  triggerCommitSha          String
  triggerMergeRequestNumber Int?
  triggerMeta               Json                 @default("{}")
  status                    RunStatus
  result                    Json                 @default("{}")
  docsAffected              Boolean?
  docPrNumber               Int?
  docPrUrl                  String?
  tokenUsage                Json                 @default("{}")
  error                     String?
  attemptCount              Int                  @default(0)
  queuedAt                  DateTime             @default(now())
  startedAt                 DateTime?
  completedAt               DateTime?
  createdAt                 DateTime             @default(now())
  updatedAt                 DateTime             @updatedAt
  attempts                  AnalysisRunAttempt[]

  @@unique([repositoryId, triggerCommitSha, triggerType])
  @@index([repositoryId])
  @@index([status])
  @@index([repositoryId, createdAt(sort: Desc)])
  @@index([repositoryId, status, createdAt(sort: Desc)])
  @@index([provider, triggerCommitSha])
  @@map("analysis_runs")
}

model AnalysisRunAttempt {
  id            String        @id @default(uuid())
  runId         String
  run           AnalysisRun   @relation(fields: [runId], references: [id], onDelete: Cascade)
  attemptNumber Int
  status        AttemptStatus
  error         String?
  startedAt     DateTime      @default(now())
  finishedAt    DateTime?
  createdAt     DateTime      @default(now())

  @@unique([runId, attemptNumber])
  @@index([runId])
  @@index([status])
  @@map("analysis_run_attempts")
}

model WebhookDelivery {
  id                     String        @id @default(uuid())
  provider               VcsProvider
  deliveryId             String
  eventType              String
  providerInstallationId String?
  providerRepositoryId   String?
  signatureValid         Boolean
  payloadHash            String
  receivedAt             DateTime      @default(now())
  processedAt            DateTime?
  status                 WebhookStatus @default(received)
  error                  String?

  @@unique([provider, deliveryId])
  @@index([provider, eventType, receivedAt(sort: Desc)])
  @@index([provider, providerInstallationId, receivedAt(sort: Desc)])
  @@index([provider, providerRepositoryId, receivedAt(sort: Desc)])
  @@map("webhook_deliveries")
}
```

## Query Patterns This Schema Optimizes

- Installation sync by `(provider, provider_installation_id)`.
- Repository list by `installation_id` and `is_active`.
- Run history by `repository_id` and `created_at DESC`.
- Run filters by `repository_id`, `status`, and time window.
- Dedup pre-enqueue by `(repository_id, trigger_commit_sha, trigger_type)`.
- Webhook replay protection by `(provider, delivery_id)`.

## Issue 1.4 Compatibility

Issue **1.4** originally asked for GitHub-named tables/fields (`installations.github_id`, `repositories.github_id`, `analysis_runs.commit_sha`). The implementation skips the GitHub-only interim and goes directly to the provider-agnostic v2 schema. This is a deliberate deviation from the roadmap sequence: since no production data exists yet, there is nothing to migrate and no compatibility layer is needed.

The v2 schema fully satisfies the functional requirements of issue 1.4 for GitHub while being ready for additional providers.

## Suggested Migration Plan

1. `bun db:migrate` — runs `prisma migrate dev`, which generates and applies the initial SQL migration for all new tables.
2. Add seed data if needed (`prisma db seed`).
3. `bun db:studio` — opens Prisma Studio to verify models and data.

To regenerate the Prisma client after schema changes: `bun db:generate`.

## Retention and Partitioning

- Keep installation/repository tables unpartitioned.
- Partition `analysis_runs` and `analysis_run_attempts` monthly when run volume justifies it.
- Keep full JSON payloads hot for 90 days, then archive/prune large blobs while preserving summary metrics.

## Minimal ERD (v2)

```text
Organization (auth) (1) ───< provider_installations (1) ───< provider_repositories (1) ───< analysis_runs (1) ───< analysis_run_attempts
                                                                                                        \
                                                                                                         \────< webhook_deliveries (linked by provider + external IDs, no FK)
```
